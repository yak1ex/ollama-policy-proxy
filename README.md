# Ollama Policy Proxy

Ollama Policy Proxy is a small HTTP proxy that applies configurable inference defaults before forwarding requests to one Ollama server. It is useful when a client cannot set Ollama's `think` field or should use a consistent inference profile.

```text
Ollama client  ->  policy proxy  ->  Ollama server
```

The proxy does not perform inference, translate APIs, download models, or inspect responses. It modifies JSON bodies only for `POST /api/chat` and `POST /api/generate`. Other requests pass through without body transformation.

## Requirements and installation

- Python 3.11 or newer
- [`uv`](https://docs.astral.sh/uv/)
- An Ollama server for normal use; automated tests use a mock upstream

Install the locked environment from the project directory:

```shell
uv sync
```

Copy [`config.example.yml`](config.example.yml) and edit its upstream URL and policies. Start the proxy with:

```shell
uv run ollama-policy-proxy --config config.yml
```

The example binds to `127.0.0.1:11435` and forwards to `127.0.0.1:11434`.

## Configuration

```yaml
upstream:
  url: http://127.0.0.1:11434
  connect_timeout: 10
  read_timeout: 300

server:
  host: 127.0.0.1
  port: 11435
  max_policy_body_bytes: 67108864

defaults:
  think: false
  options:
    num_predict: 2048

models:
  "qwen3:8b":
    think: false
  "gpt-oss:20b":
    think: medium
    options:
      num_predict: 8192

profiles:
  fast:
    think: false
    options:
      num_predict: 1024
  reasoning:
    think: high
    options:
      num_predict: 8192
```

`upstream.url` must be a fixed absolute HTTP or HTTPS URL without a query or fragment. Clients cannot select another destination. Server host defaults to loopback, the port defaults to `11435`, connection timeout defaults to 10 seconds, and upstream idle-read timeout defaults to 300 seconds.

Configuration is validated before the server starts. Unknown keys, invalid types, missing upstream configuration, and invalid ports or URLs produce an actionable `configuration error` message.

### Policy precedence

Precedence from highest to lowest is:

1. Explicit request fields
2. Selected profile
3. Exact model name
4. Global defaults

`options` merge one key at a time at every level. Missing values receive defaults; explicit `false`, `0`, and `null` values remain explicit. An explicit `options: null` is preserved rather than replaced. All other request fields—including messages, images, tools, structured-output schemas, prompts, and streaming controls—remain unchanged.

The proxy preserves the configured `think` value as a Boolean, string, or `null`. Ollama models differ in supported controls. Check a model with `/api/show` before assigning values such as `low`, `medium`, or `high`.

### Selecting a profile

Set `X-Ollama-Profile` to an exact configured profile name:

```shell
curl http://127.0.0.1:11435/api/chat \
  -H "Content-Type: application/json" \
  -H "X-Ollama-Profile: fast" \
  -d '{"model":"qwen3:8b","messages":[{"role":"user","content":"Describe a red bicycle."}]}'
```

The header is consumed by the proxy and is never sent to Ollama. An unknown profile returns HTTP `400` without contacting the upstream server. Requests without the header receive model and global defaults.

## Examples

Default non-thinking behavior from `defaults.think: false`:

```shell
curl http://127.0.0.1:11435/api/generate \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3:8b","prompt":"Write one image-generation prompt.","stream":false}'
```

Explicit reasoning overrides all configured defaults:

```shell
curl http://127.0.0.1:11435/api/chat \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-oss:20b","messages":[{"role":"user","content":"Solve 17 * 23."}],"think":"high","stream":false}'
```

List models and inspect model-specific thinking support through the same base URL:

```shell
curl http://127.0.0.1:11435/api/tags

curl http://127.0.0.1:11435/api/show \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-oss:20b"}'
```

## HTTP behavior

- `POST /api/chat` and `POST /api/generate`: parse the JSON object, apply policy, then forward it.
- `GET /api/tags` and `POST /api/show`: pass through without body transformation.
- Other methods and paths: pass through to the configured upstream, including query strings and streaming request bodies.
- Responses: preserve upstream status, reason, body bytes, meaningful headers, and incremental delivery. Hop-by-hop and framing headers are regenerated by the HTTP stack.
- Upstream HTTP errors: pass through with their original status and body.
- Connection establishment failures: return `502` with a small JSON error.
- Upstream timeouts before a response starts: return `504` with a small JSON error.
- Errors after a stream starts cannot change the already-sent status; the partial stream closes, matching normal HTTP streaming constraints.

The proxy awaits each downstream write, providing backpressure, and closes the upstream response when a client disconnects. It does not buffer upstream responses. Policy-enabled request bodies are buffered because they must be parsed and transformed; `server.max_policy_body_bytes` bounds them. Pass-through request bodies are forwarded incrementally.

Operational logs contain the method, path, requested model, and selected profile. Prompt and response bodies are not logged.

## Security and limitations

This MVP is intended for a trusted local network. It has no authentication, authorization, TLS termination, rate limiting, or per-client isolation. Loopback binding is the default.

All non-policy Ollama endpoints pass through, including model-management and administrative endpoints. Binding to a non-loopback address can therefore give connected clients the capabilities of the upstream Ollama server. Put an authenticated, endpoint-restricting reverse proxy in front if clients are not fully trusted.

Other limitations:

- One fixed upstream only; no failover or load balancing.
- Native Ollama API only; no OpenAI or Anthropic translation.
- Profiles require clients or an adjacent proxy that can add a header.
- No virtual model aliases, policy hot reload, response cache, or request history.
- The proxy does not verify that a configured thinking value is supported by a model; Ollama remains authoritative.

## Testing

Run the automated suite and quality checks:

```shell
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv build
```

The suite starts local mock upstream servers and covers policy precedence, explicit false/zero/null values, configuration errors, pass-through traffic, incremental streaming, final stream chunks, upstream errors, connection failures, read timeouts, client cancellation, and connection cleanup. It does not require Ollama.

## Manual integration with Ollama

These checks are optional and require a running Ollama server plus locally available model names. They have not been executed as part of the automated suite.

1. Start Ollama on `127.0.0.1:11434`.
2. Copy `config.example.yml` to `config.yml` and replace model names with installed models from `ollama list`.
3. Start the proxy with `uv run ollama-policy-proxy --config config.yml`.
4. Run `curl http://127.0.0.1:11435/api/tags` and compare it with port `11434`.
5. Run the non-streaming default and explicit-reasoning examples above.
6. Remove `"stream": false` and confirm NDJSON objects arrive incrementally and end with a chunk containing `"done": true`.
7. Call `/api/show` and confirm every configured `think` value appears in that model's advertised `thinking.values`.
8. Stop the client during a long stream and confirm the proxy remains responsive to `/api/tags`.

Successful manual checks establish compatibility for the tested Ollama version and models only. Record those versions when reporting results.

## Troubleshooting

- `configuration error`: read the full path in the message; startup validation identifies the invalid key or value.
- `502 could not connect`: confirm Ollama is running and `upstream.url` is reachable from the proxy host.
- `504 upstream ... timed out`: increase `upstream.read_timeout` for models that can be silent for long periods.
- `400 unknown inference profile`: add the profile to YAML or remove/correct `X-Ollama-Profile`.
- Ollama rejects `think`: use `/api/show` to inspect the model's supported values and default.
- HTTP `413`: raise `server.max_policy_body_bytes` if a transformed multimodal request legitimately exceeds the configured limit.
